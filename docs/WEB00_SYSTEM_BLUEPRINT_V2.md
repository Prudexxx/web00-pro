# WEB00 System Blueprint V2

Дата: 2026-07-03  
Роль: главный продуктово-технический blueprint WEB00 Pro 2.0.  
Источник: `WEB00 PRO 2.0 — STRATEGIC ROADMAP (MASTER FILE).md`, текущий проект и аудит-документы.

## 1. Product Definition

WEB00 Pro 2.0 = premium launch-platform для готовых сайтов бизнеса.

WEB00 — это:

- не сайт студии;
- не маркетплейс шаблонов;
- не конструктор;
- не Avito;
- не набор случайных демо;
- не dark-tech презентация возможностей.

WEB00 — это контролируемый путь запуска:

```text
выбрал готовый сайт
→ посмотрел живое демо
→ выбрал тариф
→ заполнил анкету на запуск сайта
→ получил номер проекта
→ видишь статус
→ загружаешь материалы
→ получаешь запуск и поддержку
```

Главная ценность продукта:

- клиент видит результат до оплаты;
- клиент понимает, что делать дальше;
- клиент не сталкивается с техническим шумом;
- WEB00 получает структурированную заявку, а не хаотичный чат.

## 2. Core Loop

Главный цикл:

```text
Понял → Посмотрел → Выбрал → Заполнил → Получил статус → Вернулся
```

| Этап | Что делает пользователь | Что делает система | Что видит клиент | Следующий шаг |
|---|---|---|---|---|
| Понял | Быстро считывает оффер | Показывает hero, каталог-preview, доверие | Что WEB00 запускает готовые сайты | Перейти к каталогу |
| Посмотрел | Открывает карточку/демо | Даёт preview внутри WEB00 | Как будет выглядеть сайт | Выбрать сайт |
| Выбрал | Выбирает сайт/тариф | Сохраняет контекст выбора | Цена, срок, что входит | Заполнить анкету |
| Заполнил | Отвечает на вопросы | Валидирует и сохраняет заявку | Прогресс, summary, понятные поля | Отправить |
| Получил статус | Видит номер проекта | Создаёт проект/status shell | Следующий шаг и текущий статус | Вернуться позже |
| Вернулся | Проверяет статус/материалы | Показывает историю и действия | Что происходит сейчас | Дозагрузить материалы/связаться |

Правило: если элемент интерфейса не ведёт к core loop, он должен быть вторичным или удалён.

## 3. Product Layers

### 1. Public Website

Назначение: объяснить продукт, показать доверие, привести в каталог/анкету.  
Страницы: `index.html`, `pricing.html`, `how-it-works.html`, `cases.html`, `faq.html`, `contacts.html`.

### 2. Catalog / Demos

Назначение: доказать качество через готовые сайты и живое демо.  
Страницы: `solutions.html` сейчас, `catalog.html` возможно позже.  
Ключ: каталог — curated showcase, не marketplace.

### 3. Launch Questionnaire

Назначение: превратить интерес в структурированную заявку.  
Страница: `brief.html`.  
Публичный термин: `Анкета на запуск сайта`.

### 4. Status / Client Project

Назначение: снять тревогу после отправки заявки.  
Страница: `status.html`.  
Сейчас: frontend-preview/localStorage.  
Позже: backend-backed project status.

### 5. PWA / Mobile Shell

Назначение: быстрый доступ к статусу/кабинету с телефона.  
Страницы позже: `install.html`, `app.html`, `cabinet.html`.  
Сначала PWA, не APK.

### 6. Backend / Admin Later

Назначение: управление каталогом, заявками, статусами, материалами, безопасностью и уведомлениями.  
Не подключать до frontend contract.

## 4. Target Users

| Пользователь | Страх | Вопрос | Экран, который закрывает страх |
|---|---|---|---|
| Нетехнический предприниматель | Не поймёт процесс, переплатит, не получит результат | Что я получу и когда? | Главная, Как это работает, Статус |
| Эксперт/консультант | Сайт будет выглядеть непрофессионально | Есть ли пример под меня? | Каталог, карточка сайта, демо |
| Малый бизнес | Заявки не будут приходить | Как сайт будет принимать заявки? | Каталог, тарифы, анкета |
| Продвинутый клиент | Нужны детали, сроки, объём работ | Что входит и что можно настроить? | Тарифы, карточка сайта, анкета |
| Админ WEB00 | Хаотичные заявки, нет контроля статусов | Где данные и что делать дальше? | Будущая админка/backend |

## 5. UX Language Rules

Публичный язык должен быть человеческим.

| Не показывать клиенту | Использовать |
|---|---|
| Бриф | Анкета на запуск сайта |
| SEO-база | Готов к продвижению в поиске |
| Performance | Быстро загружается |
| Accessibility | Удобен для всех |
| 2FA | Вход с подтверждением |
| Demo viewer | Предпросмотр сайта |
| Bug report | Сообщить об ошибке |
| Backend | не показывать клиенту |
| localStorage | не показывать клиенту |
| API | не показывать клиенту |

Внутри кода старые названия могут оставаться до cleanup, но публичный UI должен говорить человечески.

## 7. Core Screens

01 Главная  
Роль: понимание за 5 секунд. Содержит offer, CTA, preview каталога, доверие.

02 Каталог  
Роль: curated showcase. Содержит фильтры, карточки, демо, запуск.

03 Карточка сайта  
Роль: объяснить, кому подходит сайт, что входит, цена, срок, CTA.

04 Предпросмотр сайта  
Роль: живое демо внутри WEB00, с fallback "Открыть отдельно".

05 Анкета на запуск  
Роль: structured lead capture. 4 шага, progress, autosave later.

06 Успех / номер проекта  
Роль: дать подтверждение, номер, ссылку на статус.

07 Статус проекта  
Роль: снять тревогу после заявки, показать следующий шаг.

08 Кабинет  
Роль: будущий project shell: материалы, сообщения, уведомления.

09 Установка на телефон  
Роль: PWA install, QR после заявки/status/contact.

10 Контакты / помощь  
Роль: поддержка и быстрые вопросы.

## 8. Catalog Model

Каталог = curated showcase.

Должно быть:

- фильтры;
- категории;
- карточки;
- живое демо;
- сравнение 2-3 сайтов;
- подбор по задаче;
- блок "не знаете, что выбрать?";
- кнопка `Запустить`.

Карточка сайта:

- название;
- кому подходит;
- цена;
- срок;
- бейджи;
- preview;
- demo CTA;
- launch CTA;
- modal/detail screen.

Запрещено:

- шум marketplace;
- случайные разноцветные карточки;
- большие агрессивные кнопки в обычном состоянии;
- Telegram-бот как готовое решение, если это не утверждено отдельно.

## 9. Demo Model

Предпросмотр сайта:

- открывается внутри WEB00;
- не теряет кнопку `Запустить`;
- имеет fallback `Открыть отдельно`;
- не уводит пользователя без пути назад;
- должен иметь desktop/mobile preview policy;
- на мобильном должен быть понятен режим просмотра.

Риск текущего состояния: iframe может показывать demo как мобильную версию внутри мобильного WEB00. Для premium UX нужен режим "desktop preview" или явный переключатель.

## 10. Questionnaire Model

Анкета на запуск сайта:

- 4 шага;
- progress;
- автосохранение later;
- summary справа на desktop;
- summary после шагов или sticky block на mobile;
- понятные поля;
- загрузка логотипа/материалов later;
- проверка перед отправкой.

Шаги:

1. Выбор сайта и тарифа
2. О бизнесе
3. Материалы
4. Проверка и отправка

Поля:

- ниша;
- название бизнеса;
- услуги/товары;
- контакты;
- стиль/настроение;
- примеры сайтов;
- домен;
- заявки;
- блог/статьи;
- логотип/фото;
- комментарий.

## 11. Status Model

После отправки клиент видит:

- номер проекта;
- текущий статус;
- следующий шаг;
- связь;
- загрузку материалов;
- историю.

Клиентские статусы:

1. Анкета получена
2. Материалы проверяются
3. Сайт настраивается
4. Проверка качества
5. Ожидает согласования
6. Готов к запуску
7. Запущен
8. Поддержка

Важно: пока backend нет, статус не должен обещать real account/auth/payment.

## 12. Cabinet Model

Кабинет — future layer, но frontend-shell можно готовить.

Разделы:

- мой проект;
- статус;
- материалы;
- сообщения;
- уведомления;
- паспорт качества;
- поддержка;
- безопасность входа.

Кабинет не должен быть сложной CRM. Он должен отвечать на вопрос клиента: "что сейчас с моим запуском и что нужно от меня?"

## 13. PWA Model

Сначала PWA, не APK.

Будущие страницы:

- `install.html`
- `app.html`
- `cabinet.html`

QR-code показывать:

- после отправки анкеты;
- в статусе;
- в кабинете;
- в контактах/help.

QR-code не ставить в hero: он отвлекает до возникновения ценности.

Цель PWA:

- открыть статус в один тап;
- получить уведомления later;
- иметь кабинет на телефоне.

## 14. Security Model

Публичная заявка:

- без обязательной регистрации;
- с защитой от спама.

Нужно позже:

- rate limit;
- honeypot;
- duplicate detection;
- suspicious queue;
- CAPTCHA/Turnstile только при подозрении;
- подтверждение контакта.

Кабинет:

- вход с подтверждением;
- optional 2FA для клиента;
- session control.

Admin:

- MFA обязательно;
- audit log;
- роли;
- no secrets frontend.

## 15. Quality Passport

Публично писать человечески:

- Быстро загружается
- Готов к продвижению
- Удобен на телефоне
- Проверен перед запуском
- Поддержка после запуска

Внутри можно хранить:

- performance score;
- SEO checks;
- accessibility checks;
- mobile-ready;
- launch time.

## 16. Visual Canon

Light premium:

- paper/cream background;
- `#8E0F13` accent;
- black serif headings;
- clean sans UI;
- thin borders;
- no neon;
- no dark-tech;
- no visual noise;
- strong editorial rhythm.

## 17. Responsive Canon

Поддержать:

- 360
- 375
- 390
- 414
- 430
- 768
- 1024
- 1280
- 1366
- 1440
- 1536
- 1920

Логика:

- mobile: один столбец;
- tablet: 2 колонки, где это усиливает чтение;
- desktop: полноценная сетка;
- mobile desktop-mode: не должен ломать ширину и создавать двойные scrollbars.

## 18. Performance Canon

Цели:

- LCP <= 2.5s
- INP <= 200ms
- CLS <= 0.1

Правила:

- один hero visual;
- размеры у изображений;
- lazy ниже первого экрана;
- без тяжёлого видео в hero;
- не блокировать main thread;
- не грузить лишние CSS-слои после cleanup.

## 19. Accessibility Canon

Обязательное:

- labels;
- focus-visible;
- keyboard navigation;
- ESC для модалок;
- не только цвет для ошибок;
- большие touch targets;
- aria-expanded для menu/accordion;
- понятные тексты.

## 20. SEO Canon

Обязательное:

- уникальный title/description;
- один H1;
- canonical;
- sitemap;
- robots;
- OpenGraph;
- понятные URLs;
- без тестовых страниц в sitemap.

## 21. Product Principles

1. Каталог — ядро.
2. Не заставлять регистрироваться до заявки.
3. Не использовать жаргон.
4. Не смешивать premium и low-tier цены.
5. Не делать главную простынёй.
6. Не делать публичную кнопку ошибки главной.
7. Не обещать backend до реализации.
8. Не делать APK до PWA.
9. Не ломать адаптив.
10. Не добавлять фичу, если она не ведёт к core loop.
