# WEB00 Canonical Live Catalog Design

## Purpose

WEB00 production must expose the backend database as the only live catalog source while preserving owner changes made through the Admin UI. The 15 canonical cards are published by default for new clean databases, the existing production draft canonical rows are promoted once, and newly created Admin UI sites remain private drafts.

## Current Faults

1. The canonical snapshot builder emits every site with `status="draft"` and `publishedAt=null`, so a clean production database starts with 15 private cards.
2. Production already has canonical rows, so changing only the seed snapshot would not promote existing rows because `seedWeb00Catalog` intentionally never overwrites owner-owned records.
3. Admin JSON requests refresh and replay once after an expired access token, but Admin multipart uploads return the first `401 UNAUTHORIZED` without refresh/replay.
4. The release frontend can fall back from a valid API empty result or API failure to static catalog data, and a sessionStorage catalog cache can keep deleted or unpublished cards visible after the backend changed.

## Canonical Snapshot Contract

For new clean databases, `backend/scripts/build-catalog-snapshot.ts` must emit the 15 canonical sites with:

- `active=true`;
- `status="published"`;
- `publishedAt` equal to deterministic snapshot `generatedAt` (`2026-07-24T00:00:00.000Z`);
- unchanged sort order, preview image URL, gallery images, feature text, prices, demos, and category mapping.

`backend/scripts/verify-catalog-snapshot.ts` must accept and verify this published snapshot contract. `backend/prisma/seed-data/web00-catalog.json` must be regenerated by the approved builder, not manually rewritten around the builder.

`seedWeb00Catalog` remains create-only for missing snapshot rows. It must not overwrite existing title, descriptions, category, features, tags, URLs, images, price, sort order, featured flag, views, status, `publishedAt`, `active`, or deletion state. If a canonical row is edited, unpublished, soft-deleted, restored, or permanently deleted by an owner, repeated seed must report the difference as a conflict or create only a missing row, and it must not roll the owner state back.

## One-Time Production Migration

A Prisma SQL migration promotes existing production canonical rows once:

- scope: `slug IN (15 canonical slugs)`;
- only rows with `status='draft'`, `published_at IS NULL`, `active=true`, and `deleted_at IS NULL`;
- only changes `status` to `published`, `published_at` to `CURRENT_TIMESTAMP`, and `updated_at` to `CURRENT_TIMESTAMP`;
- does not touch text, category, features, tags, URLs, images, price, sort order, featured flag, views, deleted rows, inactive rows, or non-canonical rows;
- allows exactly 15 updated rows for current production or 0 updated rows for a fresh database before seed;
- errors clearly for any intermediate 1-14 update count to prevent a partially promoted canonical catalog.

Production startup remains ordinary `node dist/server.js`. Render migration execution is the only deploy-time data change. `prisma db seed` remains explicit recovery/bootstrap work and is not added to `start`.

## Admin Multipart Auth Contract

`backend/src/admin/assets/api-client.js` must make `requestMultipart` mirror the existing JSON auth behavior:

- include Bearer access token unless `auth:false`;
- do not set `Content-Type` for `FormData`;
- when response is `401` with safe refreshable code `UNAUTHORIZED`, call `refreshAccess({ signal })` once;
- replay the original multipart request exactly once with the refreshed token;
- preserve path, method, body object identity, signal, credentials, and extra request options that the multipart helper supports;
- return normalized `AdminApiError` on a second `401`;
- never log, serialize, or persist passwords, access tokens, refresh cookies, or multipart bodies.

This applies to Preview upload, single Gallery upload, and Batch Gallery upload because all three route through `requestMultipart`.

## Public Frontend Source Policy

When `window.WEB00_CONFIG.apiBaseUrl` is configured and valid:

- the production public catalog uses only `/api/sites`, `/api/sites/popular`, `/api/sites/:slug`, and category API responses;
- a valid `{ data: [] }` response is an empty live catalog, not a static fallback trigger;
- API errors with `staticFallbackEnabled=false` produce a controlled fatal/empty state, never static deleted cards;
- sessionStorage catalog result caching is disabled for API-backed production pages so a normal refresh fetches fresh backend state;
- homepage popular cards and `solutions.html` use the same policy.

When `apiBaseUrl` is empty or invalid, local static preview still reads `window.WEB00_DATA.SOLUTIONS`.

`assets/js/runtime-config.js` for production must set:

```js
staticFallbackEnabled: false
```

## Verification Contract

Local backend verification includes focused RED/GREEN tests for:

- multipart `401` refresh/replay;
- snapshot builder/verifier published defaults;
- seed preservation of edits and soft-deleted canonical rows;
- production `start` staying free of seed/bootstrap work;
- one-time migration SQL scope and partial-count guard;
- admin create staying draft and lifecycle staying editable/deletable.

Local frontend verification includes tests for:

- configured API plus empty result gives zero items and no fallback;
- configured API plus error plus fallback disabled gives fatal/empty state;
- API disabled still reads static catalog;
- repeated calls fetch fresh API data instead of sessionStorage cache;
- deleted/unpublished static fallback does not surface when API is configured;
- popular and solutions flows share the same policy.

Production verification after deploy must confirm:

- Render deployed the pushed production commit;
- health and readiness are OK;
- `GET /api/sites?limit=20&page=1&sort=sortOrder` returns `meta.total=16`;
- every canonical slug appears once;
- `drova-test-copy-20260729` appears once, remains published, and is last because `sortOrder=999`;
- no drafts or duplicate slugs are returned by the public API.
